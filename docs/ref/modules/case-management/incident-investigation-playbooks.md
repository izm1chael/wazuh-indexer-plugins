# Built-in investigation playbooks

The collaboration response contains current-state recommendations for three versioned built-in checklists: initial triage, high-severity review, and linked-finding review. Eligibility is reevaluated server-side when the incident owner explicitly applies one through POST /_plugins/_setup/incidents/{id}/apply-playbook?expected_revision=N with only template_id and version. The independent playbook_apply action grant is required. Recommendations use incident status, owner, severity and aggregate finding count; no source visibility or proof of malicious activity is inferred. Linked finding review instructs analysts to inspect only accessible findings.

Each apply creates the entire checklist in one revision CAS and audit outbox event. Generated task IDs include incident ID, revision and ordinal. Immutable application receipts contain version, actor, timestamp, revision and exact task IDs. Repeat application of the same template version conflicts; changed revisions require reload. Existing manual tasks are not merged by title. The 100-task cap is shared; insufficient room rejects the whole operation. Legacy documents without playbook_runs are treated as empty history. Template versions must not be changed in place. No automatic trigger, schedule, custom rules, endpoint commands, external connectors, or arbitrary task payload are registered. Applying a checklist does not perform or verify any investigation step.

Local qualification must validate the template conditions, concurrent revision conflicts, crash/outbox recovery, permission matrix, mapping upgrades and historical receipt preservation. The next automation stage can reuse the pure eligibility and bounded task creation rules only after a trusted automation identity, activation/version policy, event delivery and replay contract are established.
