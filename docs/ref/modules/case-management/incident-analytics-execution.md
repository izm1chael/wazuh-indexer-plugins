# Sentinel-style analytics execution over native Wazuh findings

Status: opt-in development candidate; not production qualified. This supersedes the earlier *unregistered* correlation execution foundation documented in incident-correlation-execution.md. No change to the native Wazuh detection engine, decoder/rule content or endpoint security. No new TIP features.

## Delivered

1. Analyst authors an immutable correlation policy (selected native rule UUIDs, fixed UTC window 5–1440 minutes, minimum findings 2–100) and previews it under their own findings permissions. Existing policy versions remain immutable and stored as preview_only (saving alone never activates execution). The dashboard calculates a local SHA-256 approval entry from the saved definition. An operator approves an exact UUID, version and content hash.
2. Dedicated HTTPS execute/status routes at /_plugins/_setup/incident-analytics/execute and /status; no dashboard execution proxy. Exact four-field body: policy_id, policy_version, from, until (canonical UTC seconds). Strict duplicate/trailing JSON handling, 4 KiB request. Both gates default off; execution requires separately approved service principal and exact saved policy content.
3. Each execution uses one complete aligned tumbling policy window, at least 120 seconds after end and at most seven days old (start). Search native wazuh-findings-v5* using original authenticated caller context, fixed rule UUID filters, no arbitrary indices/query DSL. Maximum 100 finding observations, 20 eligible groups, 15s search timeout, one execution per service instance and 120s cooperative execution budget. No silent partial results: reject missing identities, conflicting/excluded observations, duplicates, missing versions, excessive groups, failed shards and non-exact totals. Group by cluster + agent + rule UUID, threshold per group. Capture eligible findings under the same original caller and verify search version and extracted grouping identity before creating incidents. No raw source leaves the capture boundary.
4. Durable create-only per-window reservation with plan digest binding the exact candidate references and versions, group membership and counts. Existing correlation coordinator reserves each deterministic group, creates or reconciles its deterministic incident UUID and verifies creation activity before writing group completion. After all groups verify, write immutable window completion, including zero-match windows. A failed run may leave reserved windows and some already-created incidents; this is not a multi-document transaction. Identical plan/actor retry uses deterministic receipts; changed membership/version blocks rather than silently mutating incidents. A completed window is terminal and is not searched again by the runner. Late data after completion is not automatically processed. 120s grace is NOT an ingestion watermark or proof of completeness.
5. Lightweight Python standard-library scheduled runner with SQLite durable local cursor, file lock and fair rotation. One due window per policy per invocation, at most ten per invocation, at most twenty configured policies. Read server status first; advance only after matching completed receipt (run ID verified against deployment, policy, version and window, actor and count/chronology checks). A lost response can reconcile via status; a blocked window is not skipped. Uncompleted windows older than seven days stop that policy. Logs only policy ID/version/window and coarse outcome; no credentials, finding source, raw errors or response bodies.
6. Dashboard analytics rule design/preview and execution-health pages. Inspect up to ten operator-specified aligned windows with distinct completed, reserved, not_recorded and unavailable states. Missing receipt is not evidence a policy was scheduled; reserved does not prove failure or absence of created cases. Completed group counts include replays, not necessarily new incidents. No automatic action or disclosure to AI providers.

## Activation and access

Do not activate until disposable qualification is complete. All nodes must agree on configuration and clock. Example opensearch.yml (values are examples, not actual credentials):

```yaml
plugins.setup.incidents.enabled: true
plugins.setup.incidents.analytics.enabled: true
plugins.setup.incidents.analytics.deployment_id: "00000000-0000-4000-8000-000000000001"
plugins.setup.incidents.analytics.actor: "wazuh-analytics-runner"
plugins.setup.incidents.analytics.policies: "00000000-0000-4000-8000-000000000002:1:954f740e1b4222a972f26ae88dda15cddad8480f763de73f1fb180dee1185778"
```

Use a unique stable deployment UUID, exact dedicated authenticated account name, and comma-separated reviewed saved policy UUID:version:SHA-256 entries (max 20). Hash example corresponds to policy UUID ...0002, version 1, window 15, threshold 2, single rule ...0003; use actual saved definition, not the example. Fingerprint length-prefixes UTF-8 fields (4-byte big-endian length), in order: wazuh-analytics-policy-v1, policy UUID, version decimal, window minutes decimal, threshold decimal, sorted rule UUIDs. Browser WebCrypto fingerprint from load/save is a convenience, not an approval action. Independent verify when qualifying. Configuration is node-scoped, requires controlled restart/update across nodes; no dynamic UI activation. Stop timer before disabling/changing approvals. Do not change deployment identity or service actor while receipts are in use; migration requires separate reconciliation.

Permissions: analytics_read for receipt health, analytics_execute for run, plus the approved service account's actual native finding search and concrete GET permissions. Do not give ordinary analysts the execution grant or grant the runner admin/direct hidden-index privileges. Execution grant alone is insufficient: account, approval hash and feature gates enforced. Fixed internal persistence stashes context only for known policy/case/receipt indices; source search and capture restore original authenticated caller. Validate DLS/FLS in live system. Deployment-wide shared case boundary means service account visibility must be appropriate for the SOC; there is no per-incident ACL. Receipt health grant sees attributed run counts; no raw source.

Opt-in hidden strict state indices .wazuh-analytics-runs-v1 and .wazuh-correlation-execution-v1; do not apply native findings retention. Existing incident and policy indices unchanged in this phase. No automatic receipt purge/archival: long-running deployment requires a separately designed retention/scale policy preserving replay identity. No cluster-wide lock; single-host runner and one service-instance permit, deterministic create-only receipts defend duplicate creation. A competing node can cause a retryable conflict. Do not run multiple schedulers.

## Runner

See examples/analytics-runner.example.json and example service/timer. Substitute a real TLS hostname, trusted CA file, deployment UUID, account, approved saved policy UUID/version/window and aligned first start. Start time must be explicit; never silently skip a backlog. Configure runner directory and protected credentials (WAZUH_ANALYTICS_PASSWORD) outside repository; do not place password on command line. The runner requires HTTPS certificate/hostname validation, no redirects or environment proxy, and stores no credentials in SQLite. Keep state directory owned by the dedicated local account, backed up and not shared between unrelated deployments. Use one-shot invocation on isolated qualification first:

```sh
python3 tools/incident_analytics_runner.py --config /etc/wazuh-analytics/runner.json --state /var/lib/wazuh-analytics/cursor.sqlite
```

Only after approval, adapt/install example service/timer on a single host. They are examples, not installed/enabled. The existing Docker Wazuh host can use host scheduler or dedicated sidecar later. Network timeout does not cancel indexer writes; next invocation status-checks first. Never delete a cursor or a reservation to clear errors; inspect receipts and reconcile. For reserved runs with missing/changed source, no automatic reconciliation/skip API is exposed; manual qualified maintenance remains required. A completion already recorded is recoverable without source reread. No proof of source completeness.

## Integrated qualification gate

- Build final matched indexer/dashboard RC2 heads; execute full Gradle, Jest, Python static and runner tests. Verify actual index initialization, default-off behavior, upgrades, backup/restore, native detection paths unchanged.
- Test exact action grants, principal mismatch, missing/incorrect/duplicate approval hash, unapproved policy, saved policy missing or noncanonical, direct backing-index denial, spoofed actor/index/deployment, disabled gates on each node. Use actual OpenSearch Security role matrix; verify caller context restoration through privileged policy/status callbacks, DLS/FLS and concrete GET version revalidation, no system search fallback. Verify no raw source or hashes exposed by health/incident summary.
- Test aligned closed windows, 120s boundary, seven-day backfill, rule filters, missing identity, 100/101 findings, 20/21 groups, duplicates, partial shard/timed-out search, changed source seq/primary term and permission revocation during capture. Validate both native rule UUID field variants against actual mappings. Empty/below-threshold windows complete but do not create incidents. No assumption of ingestion watermark.
- Crash/failure injection after each reserve, group create, audit delivery, group completion, window completion and cursor commit. Verify deterministic IDs, one creation audit, exactly one terminal receipt, no second incident, no overwrite of analyst changes, late membership change blocked, restart after lost response, two nodes concurrent, orphan/corrupt receipts fail closed. A reserved window can contain successful groups; test operator recovery procedure before enabling. Completed late arrivals are not auto-admitted.
- Run mocked and real TLS runner tests, wrong CA/hostname, redirect denial, wrong deployment/actor, malformed receipt, clock skew, local lock, persisted cursor after process restart, policy rotation and backfill stop; inspect logs for leakage. Verify resource limits and scheduler cadence on disposable host, then document operational backfill/late-arrival/retention policy. Verify actual systemd example if selected.
- Browser: immutable rule authoring/preview, exact fingerprint reference vector, read-only health with missing/reserved/completed/unavailable distinctions, no execution proxy, stale view and authorization errors. Run only after both forks are at final heads.
