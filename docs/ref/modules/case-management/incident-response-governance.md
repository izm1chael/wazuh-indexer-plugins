# Incident response governance (manual tracking only)

The incident aggregate stores at most 50 response intent records under the same revision CAS and durable activity outbox as other mutations. It accepts only fixed intent labels (investigate_endpoint, review_containment, review_indicator_block, collect_evidence), a human-readable scope and reason. These are not commands or validated endpoint identities. No active-response dispatch, manager API, shell execution, webhook or external connector is invoked. No caller can supply executable arguments, an actor, a timestamp, or an execution verification state.

Workflow: an owner of a triaging/active incident requests an intent; a separately authorized actor other than the requester approves or rejects; the current owner can cancel a requested or approved intent; an authorized outcome reporter may record completed, failed or not_performed after approval. Manual outcomes are represented as reported_* and execution_verified is always false. Rejection, cancellation and reported outcomes are terminal. An unresolved requested/approved record blocks closure. Exact matching outstanding type/scope requests conflict. All mutations are revision-checked; every transition writes a distinct audit event, no deletion or editing. Once the capacity is reached, further requests are blocked; archival is future work.

Separate grants: response_read, response_request, response_approval, response_outcome. Read details through GET /_plugins/_setup/incidents/{id}/responses. Ordinary incident readers cannot retrieve the response content through summary or collaboration; generic activity exposes event kind/actor/time only. These grants are additive; incident summary read and relevant owner permissions are separate. As with other writes, a mutation result includes the incident summary. Roles are test fixtures, not production role changes.

Before automated execution: verify actual Wazuh manager/agent authorization and action allowlists, bind immutable target identity and approved parameters to an expiring approval, use a distinct execution permission and stable idempotency token, implement a bounded dispatch/reconciliation ledger and authoritative execution receipt, distinguish accepted/issued from executed/verified, handle uncertain delivery without blind retries, and qualify failure/rollback behavior. No automation may consume the free-text scope or reason as a command. No automated response rule or execution path is registered.

## Existing Wazuh issued-action records

RC2 WCS defines event.index and event.doc_id, and its active-response stream records requests written by Notifications and polled by the manager. It does not certify agent execution. The response-read grant also exposes a read-only issued-responses view for a revision-bound page of up to 25 linked findings. The original caller must be able to read both the linked finding and the response stream. The fixed query uses exact index + document ID pairs, and postfilters the same exact scalar pair in the caller-visible source. Aliases, stream names or ambiguous/missing pairs are not guessed. No executable or extra_arguments fields are requested or returned. Up to 100 issued records per page; partial or excessive results fail. The view is live, not retained evidence, does not establish dispatch caused by a governance request, and cannot verify execution. The existing stream has independent retention; expiry or permissions can hide records. No source write occurs. Validate DLS/FLS and real reference shapes before rollout.
