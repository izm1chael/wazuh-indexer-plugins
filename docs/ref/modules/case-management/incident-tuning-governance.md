# Incident-linked detection tuning review

The owner of a triaging, active or closed incident may submit an analyst-attested rule UUID, distinct lowercase SHA-256 baseline/candidate version hashes, review category, reason and up to 1,000 paired externally executed labelled holdout rows (subject to the existing 256 KiB request cap). The indexer independently recomputes the conservative gate; caller-supplied counts, gate, actor, state or rule patch are not accepted. The fixture digest uses UTF-8 wazuh-tuning-fixture-v1 newline followed by ID-sorted rows with tab-separated id, label, baseline(0/1), candidate(0/1) and newline. Opaque IDs and strict labels only. Rows are not retained; keep the independently curated fixture externally for reviewer inspection. Stored receipts validate count conservation, transition feasibility and gate. The version hashes and rule UUID are analyst-supplied references, not verified against a rule registry or source finding. Never imply provenance of actual replay execution or holdout independence.

A distinct tuning_propose grant permits owner create/withdraw; tuning_review permits an authenticated reviewer other than the proposer to accept for human review or reject. The conservative gate must pass for acceptance. No approval to deploy or execute, no patch, no external I/O. Decisions are terminal, duplicate rule/version tuples conflict unless withdrawn, 25 lifetime records per incident. All state/receipt changes reuse CAS and audit outbox. Proposal work can continue after closure without rewriting closure classification/times or requiring reopen. Current incident readers can see intentionally shared analyst-supplied proposal metadata via collaboration, not raw rows or privileged finding content. This is single-SOC scope, not tenant isolation. Reviewers must independently verify fixture digest, labels, rule versions, representativeness and actual execution. Local qualification: role union/self-review, tamper/duplicate, stale revision, cap, malformed payload, CAS/outbox, hidden indices, mapping upgrades and UI.

Review commands must repeat the exact recorded fixture SHA-256. This binds the reviewer decision to the receipt; it does not prove the reviewer independently ran or inspected the fixture.
