# Staged correlation execution reservation ledger

An internal, not registered or provisioned, create-only reservation store now provides a deterministic group-to-incident UUID mapping. The reservation ID is scoped to a trusted deployment UUID and full-policy group key; the proposed incident UUID has a distinct hash namespace. The membership digest is order independent and records exact concrete finding references without storing their raw identifiers or content in the ledger. A retry with identical immutable fields returns the existing reservation; a changed membership conflicts. Late arrivals therefore require reconciliation, not another incident or silent overwrite.

The ledger is only a reservation. It is NOT a lock, successful execution record, evidence snapshot, proof of ingestion completeness, or automatic creation mechanism. No public action, scheduler, index provisioning or incident-writing call is registered. Before activation, add an explicit trusted deployment identity, policy activation/disable and version lifecycle, ingestion completeness watermark, single-writer or CAS execution coordination, incident create-only provenance and readback verification, terminal outcomes and recovery, late arrival handling, and audit attribution. If a crash occurs after incident creation but before completion, the future coordinator must reconcile the deterministic incident UUID and immutable provenance before declaring success. Never trust a browser preview as a complete execution plan.

The strict hidden template is staged for a future isolated qualification; it must not receive a findings-retention policy. No ordinary analyst or preview role should have direct access. Test conflict and replay behavior, concurrent reservations, changed membership, wrong deployment identity, state recovery and direct-index access before wiring execution. No automation is enabled by saved policies.

## Staged internal execution coordinator

A non-registered coordinator now reserves a group, creates the deterministic incident with initial references and attributed capture receipts in revision-one activity, and writes a separate create-only completion receipt only after reading and verifying creation activity. Create conflicts reconcile immutable origin and original actor; later analyst mutations are not overwritten. The reservation remains immutable. Concurrent recovery may report a retryable conflict, but cannot allocate a second incident for the same group. Changed membership remains a conflict; no automatic append/reopen. Initial severity is explicitly informational, not inferred from detections. Neither the receipt digest nor the origin is exposed in summary/activity projections.

The coordinator is not a trust boundary. It accepts internal receipt objects, and still requires an independently qualified trusted caller, source completeness/authorization, a stable automation identity, policy lifecycle, and scheduler. Receipts must correspond exactly to group membership, but are not ingestion completeness or full source snapshots. The ledger has no worker or provisioning registration. Do not expose the coordinator through a REST route or invoke it from the preview UI. Test crash at each reserve/create/deliver/complete step, concurrent retries, collision, actor changes, late arrivals and audit verification. A retry after source expiry may require a separately qualified reconciliation path because this coordinator expects capture receipts again.
