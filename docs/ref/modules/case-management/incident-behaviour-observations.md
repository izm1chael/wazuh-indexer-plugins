# Shared behavioural observations and governed promotion

Development candidate. Default off. This increment consumes the existing rule_volume_v2 finding-volume assessment; it does not add authentication-session semantics, raw endpoint-event features, identity resolution, telemetry watermarks, a calibrated risk score or AI/agentic access.

## Enablement and authorization

```yaml
plugins.setup.incidents.enabled: true
plugins.setup.incidents.behaviour.enabled: true
plugins.setup.incidents.behaviour.rule.enabled: true
plugins.setup.incidents.behaviour.observations.enabled: true
plugins.setup.incidents.behaviour.publisher: wazuh-behaviour-publisher
plugins.setup.incidents.behaviour.approved_scopes: "<comma-separated approved SHA256 fingerprints, at most 20>"
# Independently enable only after promotion qualification:
plugins.setup.incidents.behaviour.promotion.enabled: false
```

All boolean settings default false, strings blank. Provision the fixed hidden .wazuh-behaviour-observations-v1 state index using templates/cases/behaviour-observations.json when observations are enabled; matched node configuration and strict template required. No changes to existing case aggregate mapping. Separate grants under cluster:admin/wazuh/incident/: behaviour_publish, behaviour_observation_read, behaviour_review, behaviour_promote. Fixtures do not grant direct index access. Publisher needs appropriate native findings access, a single explicitly configured authenticated username, and exact reviewed scope fingerprints. Review and promotion are human operations; publisher may not review own record. Scope hash is SHA-256 of big-endian uint32-length-prefixed UTF-8 strings ("wazuh-rule-behaviour-scope-v1", field, literal value, canonical rule UUID). Use the runner --print-scope on the reviewed config; a hash is not secrecy or authentication, and low-entropy values may be guessed. A changed entity/rule needs approval. The day is not in the scope approval; server gates historical new publications to the preceding seven days. No client-supplied statistics or finding references.

## Publication and storage

POST /_plugins/_setup/incident-behaviour/observations/publish takes exactly the same field/value/rule_uuid/day as rule-assess. Authenticate and check scope before any lookup. Deterministic observation ID = UUIDv8 from first 16 bytes of SHA256 length-prefixed domain "wazuh-rule-behaviour-observation-v1", exact actor, scope fingerprint, canonical day, with version/variant bits. Fixed server-generated first observation wins. Existing committed row returns minimal original publication receipt (no analyst review details) without rescan; validates ID, query, actor, model, coverage, counts and stored lifecycle. New observation invokes shared RuleBehaviourService under restored original caller security context, same 29-day/2,000-finding cap and complete-search guards, then stores only exact query, actor/time, model, coverage, aggregate daily counts/statistics/classification, state/revision and later review/promotion metadata. No raw findings, source references, credentials, external calls or LLM prompts. Identity is actor scoped: different publishers can generate separate observations for the same literal and rule. Policy ID/version/deployment in local runner config are operator-local, not part of server identity or a rule semantic version. The first scan is immutable by service, not tamper-resistant; late data, rule drift, DLS/FLS changes or deleted source data can change current results without changing original observation. Replay is historical metadata, not reauthorization of past source. Race conflicts reread the first valid record. One publication in flight per node; rule scan service is shared with interactive rule assessment.

The query value/rule/actor are stored in _source (value/rule/actor not indexed), assessment and review unindexed objects. Shared SOC metadata deliberately readable by observation readers regardless of current source DLS/FLS; review/promote grants return the specific affected record. Approve scopes only after data classification and sharing review, use separate narrowly authorized role/account. No per-case or per-observation ACL, tenant isolation, TLP enforcement, encryption or automatic retention; restrict backups and plan retention before deployment. Never approve secrets or restricted identities for this shared store. Review reasons are also shared. No global cap on total historical records; daily read cap 50, approved publisher scope cap 20 at one time. Changing config/actor over a day can exceed queue cap; over-cap fails rather than truncates.

## Review queue and entity prioritisation

POST /observations/day with exactly canonical completed UTC day; fixed hidden index exact query.day, exact totals and <=50 records, no partial results. Returns all recorded classifications including nonflagged; missing records do not imply policy ran or no activity. Elevated and newly_observed => unreviewed at revision 1; other classifications => not_flagged. Unreviewed elevated first, novelty second, escalation requested next, remaining by ID. Dashboard /incidents/behaviour-observations validates counts, states, chronology, unique scope and queue ordering independently; no browser publisher proxy. Groups exact same publisher/field/value, counts distinct rule observations (not findings, attacks or users), orders by awaiting review, awaiting promotion, elevated and novelty counts. No cross-publisher/field identity merging, no overlap summation, no calibrated risk. Explicit broader entity hunt pivot rechecks source access and does not automatically run or restrict to the original rule.

POST /observations/review exact {id,expected_revision:1,decision,reason} with independent reviewer and revision CAS. Allowed one-time decision dismissed, monitor, escalation_requested. Reason <=1024 nonblank trimmed no control characters. Retains attribution/time/reason and original assessment, no amendment or reopen yet. Dismissed and monitor terminal (monitor is analyst disposition, not a new monitoring job). No automatic mitigation or incident generation.

POST /observations/promote exact {id,expected_revision:2}, independent enable flag and dedicated promotion grant, only the recorded escalation reviewer. This grant intentionally allows narrowly constrained incident creation via existing IncidentWriteService (not generic create permission). Fixed informational severity, medium priority, TLP:AMBER, generic description containing only observation ID and limitations. No entity literal or sampled findings copied to case. Existing actor/request_id deterministic case creation uses observation UUID as request key; validate resulting incident ID, wait for delivered creation activity, then CAS observation rev3 promoted with linked ID and timestamp. The two writes are not atomic. If case creation commits but observation update fails or delivery remains pending, reload and retry as same reviewer; existing create deduplicates and outbox recovers. Concurrent same-reviewer promotion converges through the existing idempotency path; no escalation reversal, no automatic retry worker, no takeover if reviewer unavailable. An ordinary actor-scoped create with that exact request key and matching content can satisfy the same idempotency identity; a different payload conflicts. A promoted record points to an incident at promotion time; future case deletion or edits are not independently monitored. Observation-to-case association is stored in observation index, not a new immutable origin field in incident; case description is a human reference, not proof. Evidence attachment requires existing explicit analyst workflow and current source permissions. No arbitrary severity, incident ID, evidence, response or model parameters accepted. Dashboard can open linked incident under its normal read grant. No structured AI probe yet.

## Scheduled publisher

tools/incident_behaviour_publish_runner.py uses existing rule-behaviour configuration and local state helpers; --print-scope prints approval digest without network. Dedicated HTTPS origin/CA, no proxy/redirect, environment WAZUH_BEHAVIOUR_PUBLISH_PASSWORD, one due day per run, one local SQLite ledger per reviewed config. Use a different state file from prior local-only runner (scope includes mode shared_observation_v1); examples behaviour-publish-runner.example.json, wazuh-behaviour-publish.service.example, wazuh-behaviour-publish.timer.example. No timers installed or enabled. Acknowledge only exact server receipt including actor/query/ID, original observation timestamp, verified statistics and counts. Old committed receipt may be replayed even after seven-day backfill limit; new stale windows fail at server and local cursor never advances silently. SQLite transaction and flock protect single-host contiguous cursor; state contains scope literals and aggregate statistics/receipt hash, no raw findings or credentials. State and config are sensitive. Server row and local receipt are not distributed transactions or signed attestation. No review/promote/incident rights for scheduler.
