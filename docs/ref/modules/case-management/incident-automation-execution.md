# Sentinel-style incident automation rules

Status: opt-in development candidate; not production qualified. Extends native Wazuh findings analytics and incident management. No TIP expansion, core Wazuh changes, endpoint response or model calls.

## Delivered

- Versioned ordered rule set: one to ten rules with unique IDs, creation or supported update trigger; minimum severity and finding count, incident status, unassigned-only, required tags and optional exact originating correlation policy UUID (all versions). First matching rule wins. Each saved rule-set version can be recorded at most once per incident, including zero-change outcomes.
- Allowed actions: assign a new, unowned incident to an exact configured username; only raise severity or priority; union tags; create one human investigation task; apply one built-in version-1 investigation checklist. Existing owner and handover are not overwritten; never lower severity or priority. Assignment records first assignment timestamp but does not change lifecycle status. No directory lookup or guarantee the specified username exists. Playbooks retain their existing eligibility/capacity checks (assigned triaging/active, template conditions); an ineligible playbook blocks the entire mutation. Already-applied checklist is a no-op. No closure, reopen, task completion, TLP downgrade, suppression, response approval or dispatch. All matched rule actions and attributed receipt commit in a single CAS aggregate revision, or none commit.
- Rule authoring and preview available through the dashboard. Immutable saved policy fingerprint is server-derived SHA-256 of sorted-map JSON definition; rule order matters, tag lists canonicalized. Saving never activates execution. Preview reads an exact incident's latest delivered event, proposes the first matched rule and number of changed fields, writes nothing, not an execution reservation. Drafts can be reordered or edited and saved as a new immutable version.
- Bounded current-state automation sweep of the fixed shared incident index, 10 open incident identities per page, no finding source search, no arbitrary DSL, one in-flight tick per service instance. Reads latest delivered activity at the current aggregate revision, checks actor/time/identity, evaluates saved approved rules, uses existing optimistic concurrency and outbox. Closed or pending-audit incidents cannot be mutated. Existing automation events are not triggers. Per-case receipt includes policy ID/version/hash, rule ID, triggering/applied revision, service actor, time and changed-field count. Activity records safe rule attribution; separate history reads current aggregate receipts. Up to 50 lifetime rule-set receipts per incident; capacity exhaustion blocks a new automation rather than deleting history. Audit delivery failure leaves committed aggregate and marker, and existing outbox recovery delivers audit. Concurrent sweep or analyst write conflicts cannot overwrite later state. A repeated sweep verifies the saved hash and rule identity before skipping a recorded version.
- Trigger semantics are intentionally **latest delivered revision**, not a durable historical event stream. Creation is revision one with delivered created event; supported updates are assign, start_triage, activate, edit, attach/detach finding, tags_updated, reopen, handover_accepted. A superseded event can be missed; creation can be superseded before sweep. No replay of superseded events. A matched no-op consumes the version receipt, and only one rule set version may be active at a time. A later policy version may evaluate an otherwise eligible new human event. Preview and execution are snapshots, not atomic global queue observations.
- Scheduled runner uses standard-library Python, HTTPS with trusted CA, no proxy or redirects, protected credential, local SQLite cursor and file lock. Three pages / 30 incidents maximum per invocation, one single-host scheduler. Cursor is bound to endpoint, service account and policy ID/version/fingerprint, only advances on validated response. Counts conserve applied/no_change/skipped/pending/failed. Per-case failures/pending are reported and the sweep continues; next full sweep revisits current open incidents, not the original event. Invalid/lost page response retains cursor; repeated page safe through per-incident receipt and CAS. No cluster-wide lock or server-wide durable sweep history; operational page counts are runner logs, successful/no-op decisions durable in incident aggregate. The returned cursor is an internal incident UUID, only visible to the approved runner.

## Activation

Both incidents and automation execution must be enabled. Authoring/preview/history require incidents enabled, independent of execution flag. The following values are illustrative only; never use an invented hash for actual activation. All nodes must agree on settings. Stop runner before changing activation.

```yaml
plugins.setup.incidents.enabled: true
plugins.setup.incidents.automation.enabled: true
plugins.setup.incidents.automation.actor: "wazuh-automation-runner"
plugins.setup.incidents.automation.policy: "<saved-policy-uuid>:<version>:<exact-server-sha256>"
```

Use separate grants cluster:admin/wazuh/incident/automation_read (policy, preview, history), automation_save (immutable authoring), automation_execute (sweep only). The runner requires the last grant, exact authenticated service account, node-approved version and fingerprint, and matching request fingerprint. Do not grant runner direct hidden index privileges or analyst privileges. Saving and reading do not confer execution. Dashboard uses asCurrentUser and provides no tick proxy. Internal repository operations are fixed to the shared case/automation indices, after dedicated authorization. Shared single-SOC case scope: no per-case ACL, no source lookup. Authoring may include shared analyst usernames and task titles; do not put restricted information or secrets in policy content. Reader grant covers all saved rules, permitted case previews and receipt metadata.

Storage: .wazuh-incident-automation-v1 strict hidden policy index (initialized with incidents); additive automation_runs disabled object in existing strict .wazuh-cases-v1 mapping. Existing documents with no history are treated as empty. **Apply and verify additive mapping before starting upgraded incident writers, even when automation execution is off.** Back up first. Do not use mixed-version nodes or start timer on production prior to qualification. No purge/archive implemented. Retention must preserve receipt identities.

See examples/automation-runner.example.json, wazuh-automation.service.example and wazuh-automation.timer.example. Set actual origin, CA, account and approved policy version/hash. Copy both tools/incident_automation_runner.py and tools/incident_analytics_runner.py (shared parsing/TLS helper dependency) into the protected installation path. Protect WAZUH_AUTOMATION_PASSWORD outside repo; no command line credential. One-shot test only after disposable qualification:

```sh
python3 tools/incident_automation_runner.py --config /etc/wazuh-automation/runner.json --state /var/lib/wazuh-automation/cursor.sqlite
```

Examples are not installed or enabled. A changed rule set requires deliberate configuration and separate cursor state file, never silently reuse an incompatible cursor. Cursor reset is not historical event recovery. Runner timeout does not cancel server work. No source data or credentials in logs. Inspect service exit status and incident audit/receipts for failure investigation; no external notification integration.
