## Tuning and review

Dashboard /incidents/native-replay imports local receipt JSON; validates identity, count and exact gained/lost set differences. No server write, no browser persistence or auto-execution. Per-rule label format wazuh-native-replay-labels-v1 binds every receipt event by concrete ref and source digest; independent truth positive, negative, unknown and partition tuning/holdout. Analyst must establish label provenance and frozen holdout membership before tuning, outside this local editor. Unknown is not negative. Compare baseline/candidate TP/FP/TN/FN, lost/gained true positives, new/removed false positives. Conservative descriptive review_candidate heuristic requires >=10 labelled positives and >=10 labelled negatives in selected partition, zero unknowns, no lost positives/new false positives, >=1 improvement. Not statistical qualification, not sufficient release criterion, no confidence calibration. Never treat raw match reductions as false positive reductions. Review each changed rule, including dependencies and unrelated preview changes; this first workflow compares one existing integration and one selected rule per labelled review. No claim every changed resource has been tested. Native draft edits remain the normal tuning path; promote draft->test, refresh fingerprints, re-run tuning, use independent untouched holdout and new prospective campaign.

## Native production promotion gate

Modified actual Content Manager TransportPostPromoteAction, PluginSettings and ContentManagerPlugin. Backwards-compatible default off:

```yaml
plugins.content_manager.promotion.production_frozen: true
plugins.content_manager.promotion.approved_plan_sha256: ""
plugins.content_manager.promotion.approved_plan_expires: ""
```

All three are node settings; configure consistently on all indexer nodes before enabling, restart according to operational change control. With freeze true and blank/invalid approved hash, native Test->Custom action denies production promotion before detector lookup. Draft->Test unaffected. Native GET promotion preview unchanged. To get exact read-only plan digest use the existing POST /_plugins/_content_manager/promote with the native complete preview changes, space test and additional literal boolean review_plan_only:true. This uses native promotion permission (not scheduler account), strict JSON and existing validation/detector guard/gathering, builds engine payload and captures old versions/delete snapshots, then returns message review_plan_sha256=<64 lowercase hex> before engine promotion or consolidation. Only Test->Custom accepts review_plan_only; wrong type/duplicate/trailing keys reject. Fingerprint canonical sorted JSON object keys, array order preserved, SHA256 of plan format/target/changes/apply/delete/old_versions/delete_snapshots/engine_payload. 32MiB encoded and 128 depth limit; no raw plan returned. Object/array order differences in native engine payload may conservatively block approval; re-review rather than bypass. Approve exact digest via node config ONLY after independent historical/holdout/shadow review, frozen content and checking native preview and rollback/recovery plan. Keep freeze true, set approved hash and canonical UTC expiry (no more than one hour ahead at each gate check) consistently, ordinary native POST without review_plan_only compares actual freshly gathered digest before any engine/consolidation write. Mismatch => forbidden. Clear approval hash and expiry after controlled promotion, verify actual Custom content, detector sync and rollback path. Native underlying best-effort SAP sync and rollback semantics unchanged. This guard binds gathered plan, not entire cluster, compiled mappings, all unchanged rules, or immutable transactional state; no cross-node global lock, post-gather CAS, one-use guarantee, or automatic proof that approved hash came from replay. Operator with config/direct index privileges can bypass; restrict native promote/content write roles, direct writes, policy resets and CTI sync separately. Replay fingerprints and promotion-plan digest are distinct. Independent reviewer must reconcile them; receipt files and label assertions are not cryptographic authorization. No promotion API called from dashboard review or scheduler. No live promotion performed.

## Campaign-level evidence review and expiring operator approval

The offline tools/native_rule_campaign_review.py combines historical receipts (JSON array, sorted nonoverlapping intervals ending before campaign registration) and the exact read-only prospective SQLite ledger. Requires native preview JSON from GET /promote?space=test including all six resource lists; this narrow review path covers 1..20 existing rule UPDATEs only, no additions/removals, decoders, filters, integrations, KVDBs or policy changes. One existing integration and exact dataset/cluster/space, same pinned Test/Custom and preview fingerprints across every receipt. Revalidate counts, match-set differences, contiguous prospective windows and concrete event identities, reject repeated event references across partitions and gained/lost rules outside reviewed changes. No sampling or silent gap skip. Read cap 288 windows per partition, 30,000 total event rows, 64M input/aggregate receipt byte budget (SQLite length precheck counts characters; UTF-8 memory may be larger), max 8M chars per prospective receipt. Empty complete windows count toward elapsed shadow time, not event evidence.

Labels JSON is {historical:[...],prospective:[...]}; each label has exactly index,id,source_sha256,rule_uuid,truth. Require one label for every event and every changed rule in each partition; unknown is explicit, never negative. Independently choose untouched historical holdout and truth labels before examining candidate results; the CLI cannot establish that truth or provenance. Reviewer attestation JSON has exact author,reviewer,review_plan_sha256,reason, distinct nonblank names, digest from native review_plan_only response. These are local operator assertions, not authenticated reviewer identity or cryptographic binding between replay and native plan. Reconcile the actual plan against all evidence before approving. Example invocation:

```bash
python3 tools/native_rule_campaign_review.py --preview preview.json --historical holdout.json --state prospective.sqlite --labels labels.json --attestation review.json --output review-pack.json
```

The pack contains all changed rules, historical/prospective receipt digests, label digest, plan digest, scope, attestation, per-rule paired confusion matrices and explicit blockers. Minimum 24 contiguous prospective hours, >=10 positive and >=10 negative labels per changed rule in EACH partition, zero unknown, no lost true positives/new false positives in either partition, and at least one historical improvement per changed rule. This is a deliberately conservative descriptive heuristic, not statistically sufficient or an automatic release decision; thresholds are development defaults, real duration/volume requirements must be separately reviewed. Exit 0 means ready_for_independent_release_review, 2 writes a blocked pack, 1 invalid/unavailable input. New output file only; no network calls, content writes, native promotion, or state mutation. All packs explicitly promotion_authorized:false. Dashboard local campaign review validates all aggregate conservation and blockers independently, displays per-rule Custom/Test matrices and attested names, not actual receipt/label verification or authorization. Keep original receipt files and labels protected.

When freeze is enabled, approved_plan_expires must be canonical UTC second-resolution timestamp, strictly in future and within 3600 seconds at both initial transport and captured-plan checks. Missing, invalid or expired approval fails closed. This is a time window check, not a one-time credential, not proof that an operator set it less than one hour ago, and not a guarantee that engine/consolidation finishes before expiry. Default blank. No live setting changed. Future-dated expiry may become valid in its final hour; use short-lived reviewed config and clear immediately after use. No shared durable authorization/consumption ledger yet. Native review-only mode still gathers without writing and can run while approval missing.
